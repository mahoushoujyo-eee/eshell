# eShell 1.6.0

Release date: 2026-09-20

This release turns eShell's internals into an extension platform. SFTP and
server monitoring become built-in extensions, and the same API they use is open
to trusted third-party plugins that install, enable, disable, and uninstall
without a restart. Configuration files can now be re-read while the app is
running, so a hand edit no longer costs a relaunch.

## Extensions

### SFTP and server monitoring are now built-in extensions

Both features moved out of the core workbench into extension-owned
frontend and native implementations, driven by a shared manifest
(`extensions/builtin.json`). This is a behavior-preserving refactor: the
panels, toolbar order, split layout, translations, settings keys, Tauri
commands, and successful command payloads are unchanged, and both remain
enabled by default. Native implementations still ship inside the binary —
runtime deactivation withdraws their capabilities, it does not unload code.

### External plugins

eShell discovers trusted local ESM plugins from
`.eshell-data/extensions/*/manifest.json` and loads them through a scoped
native `plugin://` resource protocol, activating enabled plugins before the
first React render. Each plugin gets an API-v1 facade covering sessions,
SFTP, monitoring, UI contributions, namespaced storage, logging, and the
host's shared React instance. SFTP and monitoring themselves consume that
same facade.

A plugin can contribute panels and toolbar buttons, and mount an isolated
React controller. Activation choices persist in `extensions/state.json`.

**Plugins run as trusted code in the app's JavaScript context.** The facade
is a stable calling contract and resource-management entry point, not a
sandbox or a plugin-level permission system. There is no marketplace, no
signing, no automatic plugin updates, and no Node host. Install only code you
trust.

Two examples ship in the repository, both loadable with no build step:

- `examples/hello-plugin/` — the minimal case
- `examples/docker-plugin/` — a controller, async session commands, failure
  classification, its own toolbar icon, and a pure-logic module with unit tests

### Settings → Plugins

A new settings section lists the merged builtin + external catalog. Every row
can be enabled or disabled; external plugins can also be installed from a
picked folder and removed behind a confirmation dialog. Built-in extensions
can only be toggled — their code ships with the app.

Installing copies the directory to `extensions/<manifest id>/` and re-scans
the catalog, so the plugin is live immediately. The same validation runs as a
startup scan, and it runs **before** anything is copied, so a rejected install
leaves nothing behind. Installing over an existing id is the upgrade path: the
old copy is moved aside and restored if the copy fails. Removal deletes the
directory and drops the persisted activation flag, and is refused while the
plugin has an operation in flight.

**Installing, removing, and toggling need no restart. Editing plugin source
does** — there is still no file hot reload.

### Plugin toolbar icons

A plugin can supply its own icon three ways: a `plugin://` or `data:image/`
URL (typically `new URL("./icon.svg", import.meta.url).href`), a `{ src }`
object, or a host React component. A remote `http(s):` URL is **refused**
rather than fetched, so a plugin cannot turn the toolbar into a tracking
beacon. The host's built-in icon set grows from one name to twenty; an
unknown name still falls back to the puzzle rather than blanking the button.

Panels are also now opt-in: a panel starts hidden unless it declares
`defaultVisible: true`, so installing a plugin does not rearrange the dock.

## Config reload

Config files under `.eshell-data/` can be re-read while the app runs, so a
file edited outside the app no longer needs a relaunch. This covers
`ssh_configs.json`, `acp_agents.json`, `scripts.json`, `ai_profiles.json`, and
the agent context markdown.

Three ways to reach it:

- **Settings → Config Files** — each file with its own Reload button plus
  Reload all, and a per-file result saying whether the change landed, was
  already in effect, was missing, or was rejected as unparseable.
- **`reload_config`** — the MCP tool, so an ACP agent that edits a config file
  can make the host pick it up.
- **`eshell.config.reload()`** — the plugin facade. Read-only: it re-reads
  files the user already wrote and never returns their contents, so a plugin
  cannot use it to read SSH credentials.

Safety rules, each covered by tests:

- A **missing** file leaves the current value alone rather than clearing it —
  a half-written file cannot wipe your servers.
- A file that **fails to parse** is reported, never applied. The last good
  value stays in memory and the error names the file.
- Each file reports `{ file, path, changed, missing, error }`, and one broken
  file does not stop the others.

Reloading restarts nothing. An open SSH session keeps its connection (a new
profile applies to the next connection), and a running ACP agent keeps its
spawn settings until restarted.

**`known_hosts.json` is deliberately not reloadable.** It is the SSH host-key
trust store; re-reading a hand-edited copy would silently widen trust mid-session.

## Agent skills

A second agent-facing skill ships alongside `eshell-config`:
**`eshell-plugin-dev`** documents the manifest schema, the API-v1 facade, the
lifecycle, the install flow, and the trust model. It is seeded to
`.eshell-data/agent/skills/` on first launch and returned by the MCP
`read_agent_context` tool as `eshellPluginDevSkill`, so a local agent can
write a plugin without reading the repository.

`eshell-config` gains the reload workflow: an agent that edits a config file
is now told to call `reload_config` rather than tell the user to restart.

## Settings

The settings dialog is now a two-pane layout — a grouped navigation rail on
the left, content on the right — replacing the tab strip across the top. The
rail stays fixed while the content scrolls, so a long plugin list never moves
the navigation out of reach.

## Fixes

### Plugin lifecycle

- **Removing a plugin now takes its toolbar button and panel with it.** The
  loader retired a vanished plugin only on the startup path, on the assumption
  that removal required a restart. Removal became a runtime operation, so an
  `extensions-changed` application must retire too. The bundle-discovery cache
  is also replaced per reply instead of merged, so a removed plugin can no
  longer be resurrected out of it.
- An `extensions-changed` application re-reads bundle discovery but never
  re-applies a re-fetched catalog, so an out-of-order reply cannot resurrect a
  plugin the event just disabled.
- External panels are opt-in (see above), so a plugin no longer reopens its
  panel on every launch.

### Other

- Decode the plugin broker's named `input` envelope before deserializing SFTP,
  status-refresh, and session-operation payloads; preserve the legacy flat
  cache/picker arguments. Shared JS/Rust wire fixtures now verify the real
  request shapes on both sides.
- Omit empty directory parentheses from SSH connection-success notices and
  system logs. Known working directories still display as before, in both
  English and Chinese.
- Stop the server status panel from freezing on a slow link: polling now waits
  for the previous poll to finish before scheduling the next one, so a poll
  that outlasts the refresh interval no longer stacks overlapping requests
  whose results are all discarded but the last.
- Batch the five status probes into a single remote command instead of five
  sequential ones, cutting a poll from five SSH round trips to one.
- Abandon a status poll after 20s instead of the 30-minute session-command
  budget, so a stalled link cannot leave the panel frozen for the rest of the
  session.

## Upgrade Notes

- **No data migration.** `.eshell-data` files keep their existing formats and
  locations.
- Panel visibility is still not persisted. A plugin panel starts hidden, and
  opening one is per-run.
- Installed plugins keep working, but a plugin that relied on the old
  `defaultVisible` default now starts hidden. That is the intended change:
  declare `defaultVisible: true` to appear on install.
- Editing plugin source still requires a restart. Reinstalling the same plugin
  id is a shortcut: Settings → Plugins → Install from folder again.

- `npm run test` — 304 passing
- `npm run build` (vite)
